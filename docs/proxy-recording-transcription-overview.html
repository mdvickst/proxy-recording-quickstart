Recording & Transcribing Twilio Proxy Calls

We tested two ways to capture what's said on a masked-number Proxy call: Conversation Orchestrator capture rules for real-time transcription, and REST-started recording chained to Batch Transcription for a post-call recording plus transcript. This page covers how each works, what to configure, and what we learned building a working quickstart.

How a Proxy voice call is built

When participant A dials their assigned proxy number, Proxy answers and dials participant B from the same proxy number. Each call produces two call legs, each with its own Call SID, grouped under one Proxy Interaction (KI…). Both legs carry the full bridged audio.

Proxy sends interceptCallbackUrl once per interaction (before dialing B) and callbackUrl on status changes: outbound initiated, then completed.

Option 1 Conversation Orchestrator capture rules

Add a VOICE capture rule that matches the proxy number to a Conversation Configuration. Twilio then attaches real-time transcription to matching calls and writes every utterance into a Conversation. Proxy and your application don't change at all.

Configure

  • A Memory Store. It's required by the configuration.
  • A Conversation Configuration linked to that store.
  • One inbound-only VOICE capture rule per proxy number:
"channelSettings": {
  "VOICE": {
    "captureRules": [
      { "from": "*", "to": "+15551234567",
        "metadata": { "callType": "PSTN" } }
    ]
  }
}

Updates are PUT /v2/ControlPlane/Configurations/{id} with the full body, and Twilio applies them asynchronously.

What we learned

Don't use the usual bidirectional rule pair. proxy → * also matches the outbound leg Proxy places. That produces two conversations and two transcription streams per call, so every utterance is transcribed and billed twice. The inbound leg alone already contains both speakers.
  • Find a call's transcript with GET /v2/Conversations?channelId=CA…, then /Communications.
  • The Call SID is in channelId. resourceId is a transcription ID (GT…#n).
  • The text is in content.text. content.transcription holds metadata (engine, confidence).
  • The far party on a leg is labeled with the proxy number, not their real number.

Option 2 Recording API + chained Batch Transcription

When Proxy reports the outbound leg, the app starts a recording on the inbound Call SID using a Recording Configuration. That configuration is chained to a Transcription Configuration, so Twilio transcribes the finished recording automatically and posts the transcript to a webhook. No code connects the recording to the transcript.

What we learned

The intercept webhook is too early. Starting a recording from interceptCallbackUrl fails with 21220 "not eligible for recording," because Proxy hasn't bridged B yet. Proxy's callbackUrl reports the outbound leg only as initiated and then completed, with no in-progress. So we start on initiated and retry every 2s until B answers, then stop.
  • Record the inbound leg. Dual-channel puts A on channel 1 and B on channel 2.
  • Error 46009 "v2 transcription customer" means the account is flagged for Voice Intelligence v2. Support has to enable v3 before Transcription Configurations can be created.
  • The transcript is only delivered to your webhook. Store it yourself, or link a conversationConfigurationId to keep it in Orchestrator.
  • Recording media requires account auth, so serve downloads through your backend.

Proxy number pool gotchas. Proxy geo-matches on country at minimum, so a Canadian pool number can't serve US participants ("no compatible Proxy numbers"). Adding a number to the pool also overwrites its voice and SMS webhooks.
Which one? Use Option 1 when you want live transcripts flowing into Memory and Conversation Intelligence with no call-path code. Use Option 2 when you need the audio file, word-level timing, or a single post-call transcript for QA or compliance. Both can run at the same time on the same call.
